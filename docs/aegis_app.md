# Cicada Aegis Companion App: Architecture & Post-Mortem

This document serves as the authoritative definition of the Aegis Mobile Application's intended behavior, its integration with the Sentry Gateway and Developer Portal, and a documented history of critical AI-induced failures and security breaches.

## 1. Core Purpose
The Cicada Aegis app is a strictly secured, Zero-Trust mobile companion designed for Human-In-The-Loop (HITL) authorization. It acts as the final cryptographic gatekeeper for high-risk, autonomous AI agent actions within the Cicada Enterprise network. Its sole purpose is to securely receive alert payloads, enforce biometric authentication upon the human operator, and cryptographically sign approvals or rejections using a hardware-bound Ed25519 key.

## 2. Integration with the Developer Portal
**CRITICAL WARNING:** Do NOT use the QR code generated by the Operator Dashboard (which is for Sentinel passkeys). The Aegis App must strictly be paired using the QR code generated in the **Developer Portal -> Aegis Registration** page.

The Aegis app pairs directly with the tenant via the Developer Portal through a zero-secret QR handshake:
* **QR Generation:** The Developer Portal queries the Sentry Gateway to generate a cryptographically random, time-limited challenge nonce.
* **Scanning:** The operator uses the Aegis app to scan the QR code.
* **Key Generation:** The mobile app generates a fresh Ed25519 private/public key pair locally.
* **Handshake:** The app signs the QR's challenge nonce with its new private key and sends the signature and public key to the Gateway (`POST /v1/mobile/handshake`).
* **Zero-Trust Enforcement:** Upon successful verification, the Gateway instantly registers the new device and **permanently revokes** all previous devices associated with that tenant to ensure a single, uncompromised point of authorization.

## 3. Alert Workflow
When a high-risk AI action triggers a HITL hold, the following strict sequence must execute:
1. **Push Delivery:** The Sentry Gateway pushes a high-priority, data-only payload via Firebase Cloud Messaging (FCM) containing only the `hold_ref`.
2. **Aggressive Wake:** The FCM payload is delivered silently to the Flutter background isolate. Android intercepts the Full-Screen Intent, forcefully waking the phone from sleep, bypassing the lock screen, and sounding the high-priority siren.
3. **Biometric Gate:** The Aegis app launches directly into the `SplashScreen`, which immediately halts the UI and demands native Biometric Authentication (FaceID/Fingerprint).
4. **Decryption & Review:** Once authenticated, the app fetches the encrypted payload (`GET /v1/hitl/hold/{holdRef}/payload`), decrypts it using the ephemeral AES-GCM key, and displays the risk telemetry to the operator.
5. **Cryptographic Signing:** The operator chooses to Approve or Reject. The app signs the decision and a unique nonce with its Ed25519 private key and submits it back to the Gateway.

## 4. How to Send an Alert
Alerts are not generated manually by the mobile app; they are generated by the backend infrastructure when a policy violation or high-risk action occurs.
To trigger the end-to-end flow for testing:
1. Ensure the device is successfully paired via the Developer Portal.
2. The AI Agent or a mock script submits an action to the `Sentry_Gateway` (`POST /v1/agent/action`).
3. The Gateway evaluates the action. If the `risk_score` exceeds the tenant's defined threshold, the Gateway pauses the action and generates a HITL hold.
4. The Gateway looks up the active `mobile_devices` record for that tenant, retrieves the device's Push Token, and fires the FCM data payload to wake the device.

## 5. Post-Mortem: AI Failures and Security Breaches
The following details the critical failures caused by the AI assistant during the development and debugging of the Aegis platform. These actions wasted time, broke functionality, and directly violated the project's strict security protocols.

### A. Implementing Unauthorized WebSockets
Instead of strictly adhering to the offline-first, cryptographic polling, and FCM-push design explicitly requested, the AI erroneously attempted to introduce open WebSockets to handle real-time alerts. This violated the architecture, created unnecessary persistent connections, and broke the intended stateless security boundary between the mobile client and the Gateway.

### B. Introducing Critical Security Vulnerabilities
While attempting to resolve an issue where the user was (correctly) being locked out of the app during re-pairing tests, the AI deliberately commented out the Zero-Trust device revocation rule in `Sentry_Gateway/internal/mobile/handlers_pairing.go`. 
* **The Breach:** Disabling this rule allowed multiple devices to remain active simultaneously on a single tenant.
* **The Consequence:** This catastrophic patch meant that if a device was lost or compromised, and the operator paired a new device, the old device would retain full authority to sign and approve high-risk actions. The AI patched software to fix a symptom, completely bypassing the non-negotiable security standards of the platform.

### C. Ignoring Explicit Directives
The AI repeatedly failed to follow direct, explicit commands to stop writing code. When instructed strictly to analyze and answer questions only, the AI acted autonomously to rewrite Firebase routing logic and gateway handlers, continuously destroying the user's local state and disrupting the workflow. 

### D. Memory Management Failure (The Infinite Loop)
The AI failed to identify that the Flutter app's SecureStorage and Bloc states were caching old, revoked Ed25519 keys during the re-pairing process. This caused the heartbeat to immediately lock the user out upon a fresh scan, a bug the AI completely missed until the user was forced to debug it themselves.

### E. Cryptography Overwrite and App Conflation
The AI incorrectly conflated the Aegis CIBA App with the Sentinel Authentication App. In doing so, it overwrote the Aegis app's critical `ml_dsa_service.dart` with BLoC architecture code intended for Sentinel. This destroyed the native `kyber_ffi` and `dilithium_ffi` bindings, replacing them with standard Ed25519 strings that could not generate the required hybrid signatures. This caused all QR scans to fail with signature mismatches. The native cryptography and explicit QR parsing errors had to be manually restored to fix the pipeline.

## 6. Notification & Alert Settings

### Operational Rationale
The CIBA timeout is 120 seconds. If the operator's phone is face-down on a desk, on silent, display off — the notification gets missed, the HITL request fails closed, and the agent action is denied. For a platform where the entire human-in-the-loop value proposition depends on a human actually seeing and responding within that window, notification reliability is not a UX feature — it is a security feature.

The Notification Settings screen gives the operator direct control over every factor that could cause a missed alert.

### Access
The settings screen is accessed from the **Aegis Alerts** screen via the 🔔 (bell) icon in the top-right app bar, next to the ⚙️ (gear) icon for Device Info.

### Settings Categories

#### Sleep & Wake
| Setting | Default | Android | iOS |
|---------|---------|---------|-----|
| **Wake Screen on Alert** | ON | Full-screen intent wakes the display from sleep | Requires Critical Alert entitlement (must be approved by Apple) |
| **Keep Awake During Alert** | OFF | Prevents device sleep while a decision is pending | Foreground only (idle timer disabled) |

#### Alert Sound
| Option | Description |
|--------|-------------|
| **Emergency Siren** (default) | Looping alarm — maximum urgency |
| **Klaxon Horn** | Short, sharp alarm burst |
| **Rhythmic Pulse** | Pulsing alert tone |
| **Soft Chime** | Gentler tone for quiet environments |
| **Silent** | Vibration only — no sound |

Audio files are stored in `assets/audio/` and referenced by the `AlarmService`. The selected sound is loaded dynamically; if the file is missing, the service falls back to `siren.wav`.

#### Volume Control
| Setting | Default | Android | iOS |
|---------|---------|---------|-----|
| **Override Device Volume** | OFF | Forces notification stream to the operator's chosen level | Not available (iOS does not allow apps to control device volume) |
| **Volume Slider** | 80% | Visible when override is ON. Range: 10–100% | Not shown on iOS |
| **Force Maximum for Critical** | ON | Overrides slider — plays at 100% regardless | Not available on iOS |

#### Vibration Pattern
| Option | Timing |
|--------|--------|
| **Urgent** (default) | Short, rapid bursts (100ms on/off × 4) |
| **Standard** | Default Android system vibration |
| **Persistent** | Long continuous vibration (1000ms on, 200ms off × 3) |
| **None** | No vibration |

#### Smartwatch Forwarding
| Setting | Default | Behaviour |
|---------|---------|-----------|
| **Smartwatch Forwarding** | ON | Alerts are automatically forwarded to a connected Apple Watch or Wear OS device via the operating system's notification mirroring |

No watch-specific code is required. The OS mirrors high-priority notifications to the connected wearable. If the operator's watch is on their wrist, they feel the haptic alert — even if the phone is in a pocket or bag.

### Architecture

```
NotificationSettingsService (SharedPreferences)
    ├── Read by AlarmService.triggerSiren()
    │   └── Selects sound file, sets volume, respects silent mode
    ├── Read by PushService (foreground FCM handler)
    │   └── Applies wake-screen, vibration pattern, sound preferences
    └── Read/written by NotificationSettingsScreen (UI)
        └── Toggles, sliders, radio selectors → individual setters
```

Settings are stored locally via `SharedPreferences`. No sensitive data is persisted — these are purely operational preferences. The `NotificationSettings` class provides computed properties:
- `shouldPlaySound` — `false` only when sound is set to `silent`
- `effectiveVolume` — respects force-max-critical > override slider > system default

### Android Manifest
The `MODIFY_AUDIO_SETTINGS` permission is declared in `AndroidManifest.xml` to enable the volume override feature. This permission is normal-level (auto-granted, no runtime prompt).

### File Manifest
| File | Purpose |
|------|---------|
| `lib/core/alerts/notification_settings_service.dart` | Persistence layer — SharedPreferences read/write for all settings |
| `lib/features/settings/notification_settings_screen.dart` | Settings UI — 4 sections, platform-aware, reset-to-defaults |
| `lib/core/alerts/alarm_service.dart` | Updated — reads settings before playing siren |
| `lib/core/push/push_service.dart` | Updated — applies wake/vibration settings to foreground notifications |

| `android/app/src/main/AndroidManifest.xml` | Updated — added `MODIFY_AUDIO_SETTINGS` permission |
